| 18 | **Structured game event log, `cardtown sim -log` and a JSON Lines event stream.** This is the foundation for match metrics the user wants later ("what did players do on their first turn", "which HQ did they bring", and many more like them), and for M5 replays and M6 telemetry. Its own harness task, tier `sonnet`, because it fixes the event schema those all build on. Record the schema, the observer contract and the file format as an ADR. **Storage model:** events are the permanent record and stay small. Full state is stored only at turn starts; any other point is rebuilt by deterministic replay (#19), never stored per event (a snapshot per event is roughly 1–4 MB per game). (a) **One observer hook:** replace the scattered `logf` call sites with a single observer the `Game` notifies. It receives (1) every event as it happens and (2) a *settled* notification after each top-level step (an action, a decision, a stack resolution) once the death sweep is done, carrying a read-only view of the state. Mid-resolution states are never exposed as settled. The observer is strictly read-only: it never changes state or touches the random source, and a game runs identically with or without one. `Game.Log` stays as the default observer, so existing tests keep working. (b) **Structured events,** additively: keep `Turn`, `Kind` and `Detail` unchanged (tests match on `Kind`). Add a per-game sequence number, the acting player, phase, the card involved (name from card data, never a literal), source and target asset or instance IDs, zone, and amount. Every `Chooser` answer is an event too (decision kind, the player, the options offered, the picks), so human games in `cardtown play` can be replayed and "what did they choose" is queryable. (c) **Match records:** a match-start record (seed, decklist names, Headquarters, the first-player decider and their choice, cards mulliganed per player, and the engine build's VCS revision and dirty flag from `runtime/debug.ReadBuildInfo`, since replay is only exact on the same build), a turn-start snapshot record (full state including hidden information and deck order, both players), and a match-end record (outcome, reason, turns). (d) **CLI:** `cardtown sim -log` prints one game's events as readable text (`-seed` picks the game). `cardtown sim -events <file>` writes every game's records as JSON Lines, one object per line, match-start first in each game. Output is byte-identical for the same seed. This also satisfies #12, since it touches `cmd/cardtown/main.go`. Expose both through `Taskfile.yml` if convenient. (e) **Out of scope:** the replay command (#19), in-process metric probes, computing metrics, reports and dashboards. Acceptance cases should cover: every action kind, a decision answer and both outcome kinds appear in a sample game; each settled notification follows the death sweep (no asset at 0 health in a settled view); sim results are identical with and without `-events`; two runs with one seed are byte-identical; every JSON line parses; there is one turn-start snapshot per turn; existing tests pass unchanged. | User, 2026-10-20 (amended same day) | applied (T-0020, T-0021; ADR-0005) |

| 21 | **A sim policy that actually plays expensive cards.** **Priority: before the next wave A2 task.** In 200 starter games (T-0021 review), `RandomPolicy` deployed Saboteur 5 times, Stormfront of Ideals 5 and Unceasing Tide 13, against 270 Portent Scriveners. It picks uniformly among legal actions and ends the turn with probability 0.1, so it rarely saves up 3 Requisition, and `cardtown sim` barely exercises the abilities being built. A harness task, tier `sonnet`, adds a second random policy for `cardtown sim`. It is still random and deterministic for a seed, and it only ever picks legal actions.
