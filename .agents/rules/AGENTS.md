# Workspace Rules: Animus Mundi

## Progressive Skill Routers
Read a skill only when its trigger fires. Do not load persona skills for unrelated work.
- **Docs Front Door (`docs-concierge`):** On `@docs-concierge`, or when the user asks what tools/personas exist, what to do next, or how to launch something in the docs workflow. Read `.agents/skills/docs-concierge`.
- **Workflow Steward (`workflow-steward`):** On `@workflow-steward`, or when the user wants to check another persona's work, change how a persona, the routing rules or the build loop behave, add a board directive, or reconcile branches and worktrees. Owns `.agents/` skills, rules and task templates; asks before any change outside them and records it in that day's `.agents/steward-history/` file. Opus, main session. Read `.agents/skills/workflow-steward`.
- **Product Vision & Portfolio Lead (`pm-lead`):** On `@pm-lead`, or when asked to review or update the product vision, milestones, or portfolio view in `docs/PRODUCT_SUMMARY.md`, or when the stakeholder wants to adapt the product vision (expand, contract, pivot). Read `.agents/skills/pm-lead`.
- **FRD Authoring (`pm-frd-drafter`):** On `@pm-frd-drafter`, when asked to edit FRD 01 rules, to apply a `game-designer` Design Outcome, or to draft an FRD for a milestone that has started. Read `.agents/skills/pm-frd-drafter`.
- **Game Design Discussions (`game-designer`):** On `@game-designer` (bare to pick up a `Status: open` ruling question in `docs/design/outcomes/`, or with a topic), or when the user wants to work through a design question: a ruling, card text, a mechanic, or an open survey or keyword-matrix item. Ends with a Design Outcome Report, committed as a file in `docs/design/outcomes/` together with a directive row on the build board for `lead-architect`, then automatically dispatches the `pm-frd-drafter` subagent (`.claude/agents/pm-frd-drafter.md`) on that outcome file, and emits a prompt for `pm-lead` only when milestone scope changes. Read `.agents/skills/game-designer`.
- **Technical Architecture (`lead-architect`):** On `@lead-architect`, when a milestone starts and needs a design note, when a technical decision needs a decision record, or when the user asks for a structural review of the code (Runbook E). Read `.agents/skills/lead-architect`.
- **Build Loop Lead (`lead-architect` Runbook D):** When asked to plan, start, continue or review build tasks in `.agents/tasks/`. Always Opus, in the main Claude Code session. Read `.agents/skills/lead-architect`.
- **Rules Test Author (`rules-test-author`):** On `@rules-test-author T-NNNN`, or when a task file is at `status: tests`. Sonnet. Read `.agents/skills/rules-test-author`.
- **Kernel Engineer (`kernel-engineer`):** On `@kernel-engineer T-NNNN`, or when a task file is at `status: ready` or `changes`. Gemini Flash for `tier: flash` (the lead runs it headless with `agy -p`, Runbook D3), Sonnet for `tier: sonnet`. Read `.agents/skills/kernel-engineer`.
- **Card Town Verification (`cardtown-linter`):** When auditing specifications, engine scenario tests, or CSV balance sheets. Read `.agents/skills/cardtown-linter`.

## Source of Truth
- **Rules:** `docs/frd/01_Game_Rules_FRD.md`, made executable by `pkg/engine`. A rule change lands as FRD 01 text plus a `TestFR_*` scenario test, in the same change. Precedence and workflow: `docs/frd/README.md`.
- **Frozen FRDs (02–05):** design intent only. Do not edit or design from them; they are rewritten when their milestone starts.

## Guard Rails
- **No unattended chains:** Portfolio reconciliation via `pm-lead` starts only on an explicit human prompt; FRD edits never auto-trigger synchronization. Once the user approves a Design Outcome Report in `game-designer` and `game-designer` commits the outcome file and `BOARD.md` directive, `game-designer` dispatches the `pm-frd-drafter` subagent (`.claude/agents/pm-frd-drafter.md`) to apply that outcome file (`pm-lead` is prompted only when milestone scope changes). The build loop (`lead-architect` Runbook D) runs **one task per human prompt**: once that task is `done` or `blocked`, or needs the user (a ruling, queued as a `Status: open` stub in `docs/design/outcomes/` on the integration branch, or a Flash dispatch that `agy` could not finish), the lead stops and reports. It never dispatches another task, or starts the next deliverable, without a new human prompt. It may write the current deliverable's other tasks, but leaves them `queued`. A merge never triggers the next task. **One exception, the wave run (`lead-architect` D7):** when the user starts `go tool task wave-run` for a named wave, the runner opens one fresh headless lead session per task, and each still moves one task. Work merges only into an `autoloop/` run branch, never the integration branch (except a `Status: open` ruling stub in `docs/design/outcomes/` committed on the integration branch right before stopping on a rules question). The runner stops when the wave is complete, its task, spend or time budget runs out, or anything needs the user. Only the user merges the run branch.
- **No agent `git push`:** Agents commit locally. Push only when the user asks.
- **Worktrees (all personas):** The main checkout belongs to the user. Never switch its branch, and never stage, stash or reset changes you did not make. Work there only when it is already on the branch you need and `git status --short` is empty. Otherwise work in a temporary worktree in your session's scratch folder (the one the harness or the prompt provides, or a new folder under the system temp directory, `$env:TEMP` / `%TEMP%`, if neither gives one; never `/tmp`, which on Windows can resolve to `C:\tmp`), never beside the repository:
  ```sh
  git worktree add <scratch-dir>/<name> <branch>                       # existing branch
  git worktree add -b <new-branch> <scratch-dir>/<name> <base-branch>  # new branch
  # edit, run gates and commit inside <scratch-dir>/<name>, then before handing off:
  git worktree remove <scratch-dir>/<name>
  ```
  If `git worktree add` fails because the branch is checked out in another worktree (`git worktree list`), work there only when `git -C <that worktree> status --short` is empty. Otherwise another session is mid-edit: for the integration branch, commit to a side branch (`git worktree add -b <side-branch> <scratch-dir>/side <integration-branch>`) and ask the user to merge it later; for a task branch, stop and tell the user.
- **Path-limited commits (all personas):** Another session may share your checkout, and a bare `git commit` takes whatever is staged, including its changes, under your message. Commit only the paths you changed: `git commit -m "<message>" -- <path> <path> ...`. Never leave changes staged in the main checkout between commands; stage and commit in one step.
- **Directive numbers (all personas):** During a wave run, `BOARD.md` exists on both the integration branch and the `autoloop/` run branch, and each copy has its own `Last directive` counter. Your own branch's counter can miss a number the other branch already took (wave F, session 18: `main` and the run branch each added a different #142). So before numbering a new directive row, run `go tool task next-directive`. Its first line is the number to use: one after the highest `Last directive` on the integration branch and every local `autoloop/` branch. Set your branch's `Last directive` to that number. Run the command right before you commit, not at the start of a long session.
- **Pre-commit hook:** It is not versioned by git. After a fresh clone run `cardtown hook install`.
